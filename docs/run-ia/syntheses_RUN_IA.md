# Synthèses RUN / RUN IA

## 1. RUN IA — vision et positionnement

### **RUN IA : passer d’un RUN réactif à un RUN intelligent et apprenant**

**RUN IA** est une couche d’intelligence opérationnelle qui permet de maintenir un produit **compréhensible, fiable, maintenable et évolutif**, quelle que soit la manière dont il a été construit.

Les principaux cas d’usage adressés sont :

- gestion des bugs et incidents ;
- analyse des retours utilisateurs ;
- génération et maintien de la documentation ;
- rétro-documentation de produits peu ou mal documentés ;
- accompagnement du passage du BUILD au RUN ;
- exploitation de produits construits de manière standard ou agentique ;
- identification et pilotage de la dette technique.

Le principe central est de transformer les signaux dispersés en actions traçables :

> **Signal → Compréhension → Décision → Action → Validation → Apprentissage**

L’ambition est de passer d’un RUN qui traite essentiellement des tickets à un RUN capable de **comprendre le produit, capitaliser la connaissance et améliorer continuellement son fonctionnement**.

---

## 2. Douleurs du RUN / TMA / Offshore

### **RUN : le vrai coût n’est pas le ticket, c’est la perte de contexte**

**Le constat**  
Le RUN reste largement **réactif, fragmenté et dépendant de la connaissance humaine**. À chaque incident, une part importante de l’effort consiste à reconstruire le contexte plutôt qu’à résoudre le problème.

### **4 douleurs structurantes**

| Douleur | Conséquence |
|---|---|
| **RUN subi & “usine à tickets”** | Le quotidien absorbe la capacité d’amélioration et les mêmes problèmes réapparaissent |
| **Contexte fragmenté** | Logs, tickets, code, changements, feedback et documentation sont dispersés → diagnostic lent |
| **Connaissance fragile** | Documentation partielle ou obsolète, savoir tribal, dépendance aux experts et transferts difficiles |
| **Boucle d’apprentissage incomplète** | Cause racine, post-mortem, dette technique et documentation sont rarement reconnectés |

### **TMA / Offshore : un amplificateur plus qu’une cause**

Externaliser peut ajouter des **interfaces, délais, handovers, différences horaires et enjeux de gouvernance**. Les faiblesses de documentation, d’ownership et de pilotage deviennent alors beaucoup plus visibles.

### **Opportunité RUN IA**

**Passer d’un RUN qui traite des tickets à un RUN qui comprend le produit :**

> **Signal → Contexte → Diagnostic → Action → Capitalisation**

**Thèse :** le premier gisement de valeur de l’IA est de réduire le coût de reconstruction du contexte et de coordination — avant même d’automatiser les corrections.

---

## 3. Contexte du RUN et enjeux

### **RUN : un enjeu de maîtrise, de connaissance et de capacité à évoluer**

### **Contexte du RUN**

Le RUN concentre aujourd’hui une part importante de l’effort IT, dans des environnements souvent **complexes, hétérogènes et partiellement documentés**.

- Multiplication des **tickets, incidents, feedbacks et demandes d’évolution**
- Connaissance dispersée entre **code, outils, documentation et experts**
- Documentation souvent **incomplète ou obsolète**
- Accumulation progressive de **dette technique**
- Organisation parfois fragmentée entre **équipes internes, TMA, offshore et fournisseurs**
- Produits construits de plus en plus vite, notamment avec l’IA, mais pas toujours pensés pour leur **maintenabilité**

### **Les enjeux**

**1. Comprendre plus vite**  
Réduire le temps passé à rechercher le contexte et identifier la cause d’un problème.

**2. Capitaliser la connaissance**  
Transformer chaque incident, correction ou évolution en documentation et savoir réutilisable.

**3. Passer du réactif au préventif**  
Détecter les signaux faibles, les récurrences et la dette avant qu’ils ne deviennent critiques.

**4. Augmenter la capacité des équipes**  
Automatiser qualification, investigation, documentation et préparation des remédiations.

**5. Reprendre le contrôle du patrimoine applicatif**  
Rendre le produit compréhensible et maintenable, quel que soit son mode de BUILD ou de RUN.

> **Enjeu cible : passer d’un RUN qui traite des tickets à un RUN qui comprend, apprend et améliore continuellement le produit.**
